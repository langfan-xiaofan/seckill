## 1. 项目目标与范围

### 1.1 一句话定位

一个支持**高并发抢购**的交易系统后端：活动发布 → 用户抢购 → 支付 → 超时关闭，在压测下保证**不超卖、不重复下单**，并通过监控与对账证明系统状态可被观测和修复。

### 1.2 这个项目要证明什么

面试官看项目不问"你做了什么功能"，而是问你**遇到过什么问题、怎么定位、怎么验证**。所以本项目的目标不是功能数量，而是产出下面这五样东西：

1. **一套能自证的数字**：压测 QPS / P99 / 错误率 / 超卖数 / 重复下单数
2. **一次真实的性能优化**：pprof → 找到瓶颈 → 改 → 数字变好
3. **一个一致性问题的完整处理**：Redis 预扣与 MySQL 落库必然不一致 → 对账 → 修复 → 验证
4. **一套自动化测试**：并发正确性用 `-race` 和并发单测证明，不靠嘴说
5. **可观测**：指标、日志、火焰图三件套，能回答"线上出问题你怎么查"

### 1.3 明确不做（范围边界）

| 不做 | 原因 |
|---|---|
| 微服务拆分 | 单体分层已经能覆盖考点；拆分要额外解决跨服务事务与追踪，1~2 个月必然做浅 |
| 前端页面 | 抢购的并发无法用页面演示，压测报告和 Grafana 截图更有说服力 |
| 真实支付对接 | 用 Mock 支付回调即可，接口形状按真实回调设计 |
| K8s / 多机房 | 与后端核心能力无关，属于运维范畴 |
| 秒杀以外的电商功能 | 购物车、评价、优惠券一律不做 |
| 分库分表 | 表数据量到不了那个规模，硬上只会讲不清分片键选择 |

### 1.4 三层范围

| 层 | 内容 | 对应周次 |
|---|---|---|
| **MVP（必须做完）** | 用户注册登录（JWT）、活动与商品查询、下单、Mock 支付回调、订单查询与超时关闭、依赖全 Docker 起 | 1~2 |
| **核心（简历主体）** | Redis Lua 原子预扣、幂等下单、并发防超卖、限流、缓存三防、单测 + `-race` | 3~4 |
| **进阶（拉开差距）** | Kafka 异步下单与削峰、超时释放库存、Redis↔MySQL 对账与差异修复、Prometheus + Grafana + pprof 调优、k6 压测报告 | 5~8 |

**判断标准**：做完"核心"层就足够写进简历（约第 4 周末）；"进阶"层每完成一块，简历上多一条能讲 3 分钟的素材。

## 2. 技术栈与版本

| 类别 | 选型 | 说明 |
|---|---|---|
| 语言 | Go **1.27** | 你本机是 `go1.26.3`。`go.mod` 里写 `go 1.27` 后，`GOTOOLCHAIN` 默认 `auto` 会自动下载 1.27 工具链，不用手动升级；想固定本地版本就 `go env -w GOTOOLCHAIN=local` 并把 `go.mod` 降到 1.26 |
| HTTP 框架 | **Gin** | 中间件生态够用，路由性能不是你的瓶颈 |
| ORM | **GORM** | 注意 12.2 节列出的四个坑（软删除与唯一索引、读改写丢更新等） |
| 数据库 | **MySQL 8.0** | 事务、行锁、索引设计的主要战场 |
| 缓存 | **Redis 7** | Lua 原子扣减、幂等、分布式锁、滑动窗口限流 |
| 消息队列 | **Kafka**（KRaft 单节点） | 异步下单削峰、积压监控、重复消费与幂等 |
| 日志 | 标准库 **`log/slog`** | Go 1.21+ 内置结构化日志，不必引入 zap；重点是字段化与级别规范 |
| 监控 | **Prometheus + Grafana** | 服务暴露 `/metrics`，pull 模型 |
| 压测 | **k6** | 写断言、阶梯加压、结果可入 README |
| 调试 | **`net/http/pprof` + delve** | 你本机已有 `dlv.exe`，排查并发问题时用它看 goroutine |
| 本地依赖 | **Docker Compose** | MySQL / Redis / Kafka 一键起；监控第二套 compose |

**关于热重载**：你本机装了 `air.exe`，开发期用 `air` 自动重编译，能省掉大量等待。

### 2.1 为什么不选别的

- **不用 go-zero / Kratos**：框架会替你隐藏掉要考的东西（限流中间件、内置缓存封装）。用 Gin 自己实现，面试才有东西可讲。
- **不用 sqlc / sqlx 替代 GORM**：GORM 的坑本身是考点（12.2 节），而且你已有 GORM 经验，迁移成本低。
- **不用 RocketMQ**：Kafka 的通用性更高。代价是"延时消息"要自己用定时任务实现（见 7.5），正好多一个可讲的设计点。

### 3.2 docker-compose.yaml（依赖组件）

放在仓库根目录，与代码同级。**注意镜像地址**：按你 rag 项目里的做法替换成能拉动的镜像源。

```yaml
name: seckill-infra
```

```bash
docker compose up -d
docker compose ps            # 三个都 healthy 再往下
```

> **Kafka listener 是新手第一大坑**：`ADVERTISED_LISTENERS` 决定客户端拿到的地址。Go 服务跑在宿主机 → 用 `127.0.0.1:9092`；你要是把 Go 服务也塞进 compose → 改成 `kafka:29092`。搞错会一直连不上或超时。

### 3.4 GORM 初始化（官方建议之外的四个必设项）

```go
db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{
    Logger:                 logger.Default.LogMode(logger.Warn), // Info 级别会拖慢压测
    PrepareStmt:            true,   // 预编译，压测时省掉 SQL 解析开销
    SkipDefaultTransaction: true,   // 单条写不需要隐式事务，减少 BEGIN/COMMIT 往返
    NowFunc:                func() time.Time { return time.Now().Local() },
})
sqlDB, err := db.DB()
sqlDB.SetMaxOpenConns(100)                  // ≤ MySQL 的 max-connections
sqlDB.SetMaxIdleConns(20)
sqlDB.SetConnMaxLifetime(time.Hour)
sqlDB.SetConnMaxIdleTime(10 * time.Minute)
```

**面试会问**：为什么 `MaxOpenConns` 不能设太大？（连接是 MySQL 侧的真实线程资源，超配会导致上下文切换和内存暴涨，压测反而更慢；100 是起点，最终值要用压测调出来并能在 Grafana 上看到连接数曲线。）

## 4. 目录结构与分层约定

```
seckill/
├── cmd/server/main.go            # 只做组装：读配置 → 连依赖 → 注册路由 → 优雅退出
├── config/config.yaml
├── internal/
│   ├── config/                   # 配置加载与校验（缺密钥直接启动失败）
│   ├── handler/                  # HTTP 层：参数校验、调用 service、组装响应。禁止写业务逻辑
│   ├── middleware/               # JWT 鉴权、限流、恢复 panic、请求日志、指标打点
│   ├── service/                  # 业务逻辑与事务边界。唯一可以开事务的地方
│   ├── repo/                     # 数据访问：SQL / GORM / Redis / Kafka 都在这层收敛
│   ├── model/                    # 表结构体、领域枚举、DTO
│   ├── infra/                    # 基础设施客户端：db.go / redis.go / kafka.go / lua 脚本
│   ├── job/                      # 定时任务：超时关单、库存对账
│   └── pkg/                      # 与业务无关的工具：雪花 ID、令牌桶、singleflight 封装
├── scripts/
│   ├── k6/                       # 压测脚本
│   └── sql/                      # DDL 与初始化数据
├── docs/                         # 本文件、压测报告、火焰图
├── docker-compose.yaml
├── Makefile
└── README.md
```

### 4.1 分层铁律

1. **依赖方向单向**：`handler → service → repo`。反方向引用一次都不要出现，`repo` 里不许 import `service`。
2. **事务边界在 service**：`repo` 提供方法但**不自己开事务**，由 service 用 `db.Transaction(func(tx *gorm.DB) error {...})` 组合。这样"一次下单要写几张表"这件事只在 service 里看得见。
3. **`context.Context` 一路往下传**，包括到 GORM（`db.WithContext(ctx)`）和 Redis。压测时你才能用超时控制保护自己。
4. **错误要能翻译成 HTTP 状态码**：定义业务错误 `AppError{Code, Msg, HTTPStatus}`，handler 统一转换。别在 handler 里 `if err == ErrStockNotEnough` 满天飞。
5. **日志只在边界打**：请求进来打一条、出去打一条（含耗时与状态码）；service 内部只在**异常分支**打 Error。别每个函数都打，压测时日志本身就是瓶颈。

### 4.2 面试会问

- 为什么要分层，不分层会怎样？（答案要落到**可测试性**和**变更成本**上，不要只说"规范"）
- 事务边界为什么放 service？（因为一次业务操作跨多个 repo，事务属于业务语义）
- `context` 为什么要传到底层？（超时/取消能传导到 SQL 和 Redis，避免请求已断还在跑查询）

## 5. 数据模型与数据库设计

### 5.1 全局约定

1. **金额一律用 `BIGINT` 存"分"**，代码里用 `int64`。禁止 `float`/`decimal` 混用——浮点累加会丢精度，退款对账时你会发现账对不上且查不出原因。
2. **不使用 GORM 软删除**。`DeletedAt` + 唯一索引会互相打架：删掉的记录仍占着唯一键，新记录插不进去（12.2 节有复现方式）。
3. **所有表不带外键约束**，关联靠应用层保证。理由：外键在并发写入时会产生额外的锁，且分库分表后无法使用。
4. **时间精度用 `DATETIME(3)`**（毫秒），因为 `expire_at` 的判定需要毫秒级精度。
5. 表名字段名统一加上注释，`SHOW CREATE TABLE` 就是你的表设计文档。

### 5.2 DDL

完整 DDL 放在 `scripts/sql/001_schema.sql`，逐表建。

```sql
-- ============ 用户 ============
CREATE TABLE `users` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `username`      VARCHAR(64)  NOT NULL,
  `password_hash` VARCHAR(100) NOT NULL COMMENT 'bcrypt',
  `status`        TINYINT      NOT NULL DEFAULT 1  COMMENT '1正常 0禁用',
  `created_at`    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户';

-- ============ 活动 ============
CREATE TABLE `activities` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `title`      VARCHAR(128) NOT NULL,
  `start_at`   DATETIME(3)  NOT NULL,
  `end_at`     DATETIME(3)  NOT NULL,
  `status`     TINYINT      NOT NULL DEFAULT 0 COMMENT '0未开始 1进行中 2已结束 3已下线',
  `created_at` DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at` DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  KEY `idx_status_start` (`status`, `start_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='抢购活动';

-- ============ 商品 ============
CREATE TABLE `skus` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `activity_id`    BIGINT UNSIGNED NOT NULL,
  `name`           VARCHAR(128) NOT NULL,
  `price_cents`    BIGINT       NOT NULL COMMENT '单价（分）',
  `limit_per_user` INT          NOT NULL DEFAULT 1 COMMENT '每人限购件数',
  `created_at`     DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`     DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  KEY `idx_activity` (`activity_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品';

-- ============ 库存（并发争夺的核心表）============
CREATE TABLE `stocks` (
  `sku_id`          BIGINT UNSIGNED NOT NULL,
  `total_stock`     INT     NOT NULL,
  `available_stock` INT     NOT NULL COMMENT '可售库存，只能通过条件更新扣减',
  `sold_stock`      INT     NOT NULL DEFAULT 0,
  `version`         INT     NOT NULL DEFAULT 0 COMMENT '乐观锁版本（备用方案）',
  `updated_at`      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`sku_id`),
  -- 最后一道防线：即使应用层逻辑写错，数据库也不会出现负库存
  CONSTRAINT `chk_available` CHECK (`available_stock` >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='库存';

-- ============ 订单 ============
CREATE TABLE `orders` (
  `id`              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_no`        CHAR(20)    NOT NULL COMMENT '对外订单号（雪花ID），不暴露自增ID',
  `user_id`         BIGINT UNSIGNED NOT NULL,
  `activity_id`     BIGINT UNSIGNED NOT NULL,
  `sku_id`          BIGINT UNSIGNED NOT NULL,
  `quantity`        INT         NOT NULL DEFAULT 1,
  `amount_cents`    BIGINT      NOT NULL,
  `status`          TINYINT     NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已取消 3超时关闭 4已退款',
  `idempotency_key` VARCHAR(64) NOT NULL,
  `pay_no`          VARCHAR(64) NOT NULL DEFAULT '',
  `expire_at`       DATETIME(3) NOT NULL COMMENT '支付截止时间',
  `paid_at`         DATETIME(3) NULL,
  `created_at`      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no`  (`order_no`),
  UNIQUE KEY `uk_idem`      (`user_id`, `idempotency_key`) COMMENT '幂等兜底',
  UNIQUE KEY `uk_user_sku`  (`user_id`, `sku_id`)          COMMENT '限购1件的兜底',
  KEY `idx_user_id`         (`user_id`, `id`),
  KEY `idx_status_expire`   (`status`, `expire_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单';

-- ============ 支付流水 ============
CREATE TABLE `pay_records` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `order_no`     CHAR(20)    NOT NULL,
  `channel`      VARCHAR(16) NOT NULL DEFAULT 'mock',
  `channel_no`   VARCHAR(64) NOT NULL COMMENT '第三方支付单号，回调幂等的依据',
  `amount_cents` BIGINT      NOT NULL,
  `status`       TINYINT     NOT NULL DEFAULT 1,
  `raw_payload`  JSON        NULL,
  `created_at`   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_channel` (`channel`, `channel_no`),
```

### 5.3 三个关键设计决策

**① 为什么库存要单独一张表，而不是塞进 `skus`？**

因为库存是**高频写入、行锁争夺**的字段，商品信息是**低频写入、高频读**。分开后商品表可以放心做多级缓存和读扩展，库存表的锁冲突也不会影响商品查询。这是"按访问模式拆表"的思路。

**② 幂等键为什么直接放 `orders` 表，而不是建一张 `idempotency` 表？**

因为本项目的幂等语义就是"同一个请求返回同一个订单"。`uk_idem` 冲突时直接查旧订单返回，语义天然一致，少一张表和一次事务。代价是**无法处理"首次请求还在处理中"的窗口**——那个窗口由 Redis 层的幂等标记负责（见 7.3）。

**③ `idx_status_expire` 为什么是 `(status, expire_at)` 而不是反过来？**

扫超时订单的 SQL 是 `WHERE status = 0 AND expire_at < NOW()`。`status` 是等值条件，`expire_at` 是范围条件。在联合索引里**等值条件必须放在范围条件前面**，否则范围列之后的列无法用于定位。反过来建索引虽然也能用，但要先按 `expire_at` 扫一大批再过滤 `status`，扫描行数多一个量级。

> 用 `EXPLAIN` 验证这两条：`EXPLAIN SELECT id FROM orders WHERE status=0 AND expire_at < NOW();` 看 `key` 和 `rows`，然后把索引删掉重建一次，对比差异——这个过程本身就是面试素材。

### 5.4 面试会问

- 你们订单号怎么生成的？为什么不用自增 ID？（自增 ID 会被遍历、泄露业务量；雪花 ID 趋势递增，对 B+ 树插入友好）
- `uk_user_sku` 在限购 N 件时还能用吗？（不能。这时要用 `user_quota(user_id, sku_id, taken)` 表 + 行锁/条件更新控制累计量）
- 库存表会不会成为热点？（会，单行更新在 5k QPS 下就是瓶颈，这正是 Redis 预扣要解决的问题——第 7 章）

### 6.3 下单接口的关键设计

```http
POST /v1/orders
Authorization: Bearer <jwt>
Idempotency-Key: 9f1c8b7e-3a2d-4f11-8c6e-1b2a3c4d5e6f
Content-Type: application/json

{ "activity_id": 1, "sku_id": 1001, "quantity": 1 }
```

**响应形状随实现阶段演进，这是有意设计的**：

| 阶段 | 返回 | 前端行为 |
|---|---|---|
| MVP（同步下单） | `200` + 订单详情 | 直接跳支付页 |
| 引入 Kafka 后 | `202` + `{order_no, status: 0}` | **轮询** `/v1/orders/:order_no` 直到状态确定 |

演进的理由要能讲出来：削峰意味着请求返回时订单可能还没落库，接口必须诚实地告诉客户端"受理了但没完成"，这就是 `202 Accepted` 的语义。压测脚本也要相应改成"提交 + 轮询"的模型，这更接近真实抢购的流量形态。

**下单失败的三类响应必须区分清楚**：

| 场景 | HTTP | code | 说明 |
|---|---|---|---|
| 库存不足 | 200 | 4001 | 业务失败不是系统错误，用 200 + 业务码更利于前端统一处理；也可以选 409，关键是**全项目一致** |
| 重复提交（同幂等键） | 200 | 0 | 返回**首次**的订单，不算失败 |
| 触发限流 | 429 | 4290 | 带 `Retry-After` 头 |
| 活动未开始/已结束 | 200 | 4002 | 靠 Redis 里的活动状态快速失败，别打 DB |

### 6.4 面试会问

- 为什么下单要幂等键而不是"前端禁止重复点击"？（网络重试、用户刷新、网关重试都会产生重复请求，客户端约束不可信）
- `202` 和 `200` 的区别？（受理 vs 完成，异步化之后必须用 202，否则客户端无法区分"已下单"和"排队中"）
- 限流用 429 还是 503？（429 = 你超限了，稍后重试；503 = 服务不可用。限流场景用 429）

## 7. 核心链路设计

> 本章是全文档的重点。每一节都要做到：能画出流程图、能说出为什么这么设计、能被追问三层还答得上来。

### 7.1 下单主链路

```
① 鉴权（JWT 中间件）→ user_id
② 参数校验 + 取 Idempotency-Key
③ 活动状态校验      —— 读 Redis（未开始/已结束直接拒，不打 DB）
④ 限流              —— 用户维度 + SKU 维度令牌桶
⑤ Redis 幂等标记    —— SET idem:{user_id}:{key} NX EX 86400
⑥ Redis Lua 原子预扣 —— 库存不足即失败（绝大多数请求死在这里）
⑦ 生成 order_no（雪花）
⑧ 落库分支：
   MVP：同步事务（条件更新库存 + 写订单）
   Kafka 版：投递 order.create（key = sku_id）→ 返回 202
⑨ 更新幂等标记为最终结果（success:{order_no} / fail:{code}）
⑩ 返回
```

**为什么把校验顺序排成这样**：每一步都在用更便宜的手段挡住请求。③④⑤⑥ 全在 Redis，能在不进数据库、不产生事务的前提下拒掉 90%+ 的流量。顺序不能反：**先幂等再预扣**，否则重复请求会重复扣减库存。

**同步落库的事务内容**（MVP 阶段，`service` 层）：

```go
err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    // 1. 条件更新库存：唯一正确的扣减姿势
    res := tx.Model(&model.Stock{}).
        Where("sku_id = ? AND available_stock >= ?", skuID, qty).
        Updates(map[string]any{
            "available_stock": gorm.Expr("available_stock - ?", qty),
            "sold_stock":      gorm.Expr("sold_stock + ?", qty),
        })
    if res.Error != nil {
        return res.Error
    }
    if res.RowsAffected == 0 {          // 靠 RowsAffected 判定，不要先 SELECT 再判断
        return ErrStockNotEnough
    }
    // 2. 写订单（uk_idem / uk_user_sku 唯一索引兜底）
    return tx.Create(order).Error
})
```

**补偿逻辑（必须有）**：Redis 预扣成功但落库失败时，要把库存加回 Redis，否则库存永久泄漏。

```go
if err != nil {
    // 补偿失败不能吞掉：打 Error 日志 + 打指标，留给对账任务兜底
    if incrErr := s.rdb.HIncrBy(ctx, stockKey, "available", qty).Err(); incrErr != nil {
        s.logger.Error("库存补偿失败，等待对账修复", "sku_id", skuID, "err", incrErr)
        metrics.CompensateFailTotal.Inc()
    }
    return err
}
```

### 7.2 防超卖：Redis 预扣 + DB 兜底

**Lua 脚本**（`internal/infra/lua/deduct_stock.lua`）：

```lua
-- KEYS[1] 库存 key：stock:{sku_id}（Hash：total / available）
-- ARGV[1] 扣减数量
-- 返回：1 成功；0 库存不足；-1 库存未预热
local stockKey = KEYS[1]
local qty = tonumber(ARGV[1])

-- 未预热直接失败：宁可漏过，也绝不能放过（放过就等于超卖）
local available = redis.call('HGET', stockKey, 'available')
if not available then
  return -1
end
if tonumber(available) < qty then
  return 0
end

redis.call('HINCRBY', stockKey, 'available', -qty)
return 1
```

Go 侧调用：

```go
// 包级变量：NewScript 首次会用 EVALSHA，脚本不存在时自动回退 EVAL
var deductStockScript = redis.NewScript(deductStockLua)

res, err := deductStockScript.Run(ctx, s.rdb, []string{stockKey}, qty).Int()
```

**必须能讲清的三件事**：

1. **为什么不能 `GET` 再 `DECR`**：两条命令之间有空隙。库存 1，两个请求同时 GET 到 1，都执行 DECR 成功 → 库存 -1，超卖。
2. **为什么用 Lua 而不是 `WATCH` + `MULTI`**：WATCH 是乐观锁，冲突要自己写重试循环，高并发下重试次数爆炸；Lua 在 Redis 单线程里整段执行，天然原子，无重试。
3. **Redis 预扣成功了就一定能下单成功吗**：不能。Redis 是**流量闸门**，MySQL 是**真相来源**。这就是为什么还要 DB 侧条件更新做二次校验、以及为什么必须有对账。

**DB 侧为什么用条件更新而不是乐观锁版本号**：`UPDATE ... WHERE available_stock >= ?` 本身是原子的，由 InnoDB 行锁保证；而"查 version → 改 version"是读改写，在并发下会丢更新，除非配合重试。版本号方案在频繁冲突时重试成本高，本项目用条件更新更直接。`version` 字段保留只是为面试对比用。

**`CHECK (available_stock >= 0)` 的价值**：它是最后一道防线。就算应用层逻辑有 bug（比如某处用了 `Save` 覆盖写），数据库也不会出现负库存——错误会以"更新失败"的形式暴露，而不是变成脏数据。**它是能被测试的**：故意写一个错误扣减的单测，断言数据库报错。

### 7.3 幂等：三层防线

**重复请求的四个来源**（要能一条条说出来）：客户端网络重试、用户连点/刷新、网关或 Nginx 重试、MQ 重复投递。

**L1：Redis 幂等标记（挡住并发重复）**

```go
key := fmt.Sprintf("idem:%d:%s", userID, idemKey)
ok, err := s.rdb.SetNX(ctx, key, "pending", 24*time.Hour).Result()
if !ok {
    // 已存在：把上次的结果原样返回
    v, _ := s.rdb.Get(ctx, key).Result()
    switch {
    case v == "pending":
        return nil, ErrProcessing        // 202，让前端稍后轮询
    case strings.HasPrefix(v, "success:"):
        orderNo := strings.TrimPrefix(v, "success:")
        return s.getOrderByNo(ctx, orderNo)   // 返回首次的订单，语义与首次一致
    case strings.HasPrefix(v, "fail:"):
        code, _ := strconv.Atoi(strings.TrimPrefix(v, "fail:"))
        return nil, bizErr(code)
    }
}
// ... 后续流程
// 结束时写入最终结果（失败也要写，否则重试会重新扣库存）
s.rdb.Set(ctx, key, "success:"+orderNo, 24*time.Hour)
```

**关键点：幂等标记必须存"结果"，不能只存 `"1"`。** 只存 `"1"` 的实现，在"库存不足"和"下单成功"两种重试场景下都会返回错误的东西——前者变成"处理中"永远转圈，后者拿不到订单号。

**L2：DB 唯一索引兜底**

Redis 会挂、key 会过期（24h），所以 `uk_idem (user_id, idempotency_key)` 是最后防线。冲突时不要直接报错，而是查出已有订单返回：

```go
if errors.Is(err, gorm.ErrDuplicatedKey) {   // GORM 开启了 TranslateError
    return s.getOrderByIdemKey(ctx, userID, idemKey)
}
```

**L3：支付回调幂等**（第三方必定重试）

`uk_channel (channel, channel_no)` 唯一 + 订单状态 CAS：

```sql
UPDATE orders SET status = 1, paid_at = NOW(3), pay_no = ?
WHERE order_no = ? AND status = 0;     -- RowsAffected = 0 说明已支付或已关闭
```

**为什么用状态 CAS 而不是 `SELECT` 判断状态**：支付回调和超时关单可能同时到达。先查状态再更新，两者会同时读到 `status=0`，一个改成"已支付"、一个改成"超时关闭"，结果是**用户付了钱订单却被关掉**。CAS 让数据库来裁决，只有一个能成功。

### 7.4 削峰：Kafka 异步下单

**Topic 设计**

| topic | 分区键 | 生产者 | 消费者 | 用途 |
|---|---|---|---|---|
| `order.create` | `sku_id` | 下单接口 | 落库消费者 | 异步落库，削峰 |
| `order.timeout` | `order_no` | 定时任务 | 关单消费者 | 超时关闭（可选，见 7.5） |
| `stock.release` | `sku_id` | 取消/关单 | 库存回补消费者 | 回补 Redis 与 DB 库存 |
| `order.create.dlq` | — | 消费者 | 人工 | 重试耗尽后的死信 |

**分区键为什么选 `sku_id`**：同一商品的消息进同一分区，单商品内保持顺序。顺序性对库存释放/回补很重要（先释放 A 再释放 B，不能颠倒）。**代价是热点商品倾斜**——抢购场景下恰好是热点集中，所以要说清：真正的防超卖靠 Redis 预扣，Kafka 的顺序性只是辅助，倾斜问题用"分区数 ≥ 消费者数"和监控 lag 来控制。

**消费端必须幂等**（Kafka 是 at-least-once，重复投递是常态）：

```go
// 以 order_no 为准，重复投递时直接忽略
if err := tx.Create(order).Error; err != nil {
    if errors.Is(err, gorm.ErrDuplicatedKey) {
        return nil   // 已经落过库，提交 offset 即可
    }
    return err
}
```

**offset 提交策略**：手动提交（`CommitMessages`），**处理成功才提交**。失败重试 3 次后投递到 `order.create.dlq` 并提交 offset——否则一条坏消息会永远阻塞分区（head-of-line blocking）。这是面试高频追问点。

**积压监控**：`kafka_consumergroup_lag` 指标 + 阈值告警。扩容方式：加分区 + 加消费者实例，但**消费者数超过分区数就是浪费**（多出来的实例分不到分区）。

**客户端选型**：`segmentio/kafka-go` 上手快、API 直白；`IBM/sarama` 更经典、面试认知度高、但要自己管理 offset 细节。建议先用 kafka-go 跑通，面试前把"offset 提交与重复消费"的逻辑读明白，比选哪个库重要。

### 7.5 超时未支付释放库存

**两个方案，选 A**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 定时扫描**（选它） | 每分钟扫 `status=0 AND expire_at < NOW()` 限 200 条 | 简单、可重入、易测试；缺点是精度只有分钟级，且延迟不精确 |
| B. 延时消息 | Kafka 无原生延时主题，要自建时间轮或做多级 topic 转发 | 精度高但复杂度高，容易做成半成品 |

> RocketMQ 有原生延时消息，这一条正好是你讲"为什么选 Kafka"时的代价案例。

**扫描任务必须加分布式锁**（否则多实例会重复关单）：

```go
// 锁：SET NX EX + Lua 释放（先比 value 再 DEL，避免误删别人的锁）
locked, _ := rdb.SetNX(ctx, "lock:job:close_order", uuid, 30*time.Second).Result()
if !locked { return }
defer releaseLock(ctx, rdb, "lock:job:close_order", uuid)   // Lua: if get==uuid then del
```

**关单必须用状态 CAS**（与 7.3 的支付回调互斥）：

```sql
UPDATE orders SET status = 3 WHERE order_no = ? AND status = 0;
-- RowsAffected = 1 才回补库存；= 0 说明用户已支付或已取消，什么都不做
```

**回补库存的两个约束**：
1. 回补后 `available` 不能超过 `total`（Lua 里做上限判断），否则重放会导致**库存虚增**
2. 回补要同时改 Redis 和 DB（DB 侧用 `available_stock + ?` 但要保证不退超 `total_stock`）

**支付与关单的竞态处理**：用户支付时订单已被关单 → 回调 CAS 失败 → 走退款流程（本项目记 `status=4` + 日志 + 指标，不做真实退款）。

### 7.6 缓存设计

**缓存什么**：活动详情、商品列表、活动状态（开始/结束）。库存不走缓存回源，它本身就是 Redis 的主数据。

**Key 设计**

| Key | 类型 | TTL | 用途 |
|---|---|---|---|
| `activity:detail:{id}` | String(JSON) | 300s + 随机 60s | 活动详情 |
| `activity:status:{id}` | String | 与活动结束时间对齐 | 未开始/进行中/已结束的快速判断 |
| `stock:{sku_id}` | Hash | 活动结束后清理 | `total` / `available` |
| `idem:{user_id}:{key}` | String | 86400s | 幂等标记 |
| `limit:sku:{sku_id}:user:{user_id}` | String(计数) | 与活动对齐 | 限购计数 |

**三防（必须逐条能讲原理 + 有代码）**

**① 缓存穿透**——查不存在的数据，每次都打 DB

- 空值缓存：`SET activity:detail:999999 "" EX 60`，短期兜住（缺点是占用 key 空间，用短 TTL 换）
- 布隆过滤器：预热时把所有活动 ID 灌进去，查询前先过一遍。本地实现（`internal/pkg/bloom`）即可，不引 RedisBloom 模块：

```go
// 极简布隆：k 个哈希 + 位图。说清它的两个特性：
// 1) 判定"不存在"一定准确 → 可以直接拒绝，安全
// 2) 判定"存在"可能是假阳性 → 继续查缓存/DB，不影响正确性
```

**② 缓存击穿**——热点 key 过期瞬间，大量并发同时回源

```go
var group singleflight.Group   // golang.org/x/sync/singleflight

func (s *ActivityService) GetDetail(ctx context.Context, id int64) (*model.ActivityDetail, error) {
    key := fmt.Sprintf("activity:detail:%d", id)
    v, err, _ := group.Do(key, func() (any, error) {   // 同一 key 同时只有一个回源
        if detail, ok := s.cacheGet(ctx, key); ok {
            return detail, nil
        }
        return s.loadFromDBAndSetCache(ctx, key, id)
    })
    if err != nil { return nil, err }
    return v.(*model.ActivityDetail), nil
}
```

**③ 缓存雪崩**——大批 key 同时过期

- TTL 加随机抖动：`300 + rand.Intn(60)` 秒
- 多级缓存：本地缓存（`ristretto` 或 `bigcache`）TTL 1~5s 兜底，Redis 挂了或抖动时挡住瞬时流量。本地缓存的代价是**多实例间可能短暂不一致**，TTL 越短越安全——这就是为什么本地 TTL 只能设秒级。

**一致性：Cache-Aside**

```
读：缓存命中 → 返回；未命中 → 查 DB → 写缓存（带随机 TTL）
写：更新 DB → 删除缓存            ← 顺序不能反
```

- **为什么删缓存而不是更新缓存**：并发写时，两个请求的"更新缓存"可能以错误的顺序落地（后写的可能先到），删缓存让下次读自然回源，避免了这个窗口。
- **为什么先改 DB 再删缓存**：反过来的话，"删缓存 → 改 DB"之间会有请求把旧值读进缓存，导致长期脏数据。
- **延迟双删**：改 DB 后删一次，再延迟 500ms 删一次，覆盖"删缓存后仍有旧请求把旧值写回"的极端窗口。
- **终极方案**：订阅 MySQL binlog（canal）异步失效缓存，把缓存一致性交给数据变更流。本项目**不做但要能讲**，这是加分回答。

### 7.7 限流

**先自己实现一个惰性补充的令牌桶**（`internal/pkg/limiter/token_bucket.go`）：

```go
type TokenBucket struct {
    mu       sync.Mutex
    capacity float64
    tokens   float64
    rate     float64      // 每秒补充的令牌数
    last     time.Time
}

func (b *TokenBucket) Allow() bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    now := time.Now()
    // 惰性补充：按流逝时间算，不启后台 goroutine
    b.tokens = math.Min(b.capacity, b.tokens+now.Sub(b.last).Seconds()*b.rate)
    b.last = now
    if b.tokens >= 1 {
        b.tokens--
        return true
    }
    return false
}
```

**为什么不用 `time.Ticker` 定时补令牌**：每个限流 key 一个 ticker 就是一个 goroutine。10 万个 SKU 就是 10 万个协程在那里空转。惰性计算把成本摊到每次请求上，只有真正被访问的 key 才有开销。

**和 `golang.org/x/time/rate` 的关系**：`rate.Limiter` 就是生产级的惰性令牌桶，项目里可以先用它。但你要能讲出"我实现的版本哪里不如它"（预占令牌、动态调整速率、Wait 语义、批量获取）。

**分布式限流**（单机限流在集群下总配额会被放大 N 倍）：

| 算法 | 实现 | 缺点 |
|---|---|---|
| 固定窗口 | `INCR` + 首次 `EXPIRE`（Lua 保证原子） | 窗口边界可被 2 倍流量穿透 |
| 滑动窗口 | `ZADD` + `ZREMRANGEBYSCORE` + `ZCARD` | 内存开销大（每个请求一个成员） |
| 令牌桶 | Redis 存令牌数，Lua 里按时间戳补 | 需要存 last_refill 时间戳，实现稍复杂 |

**推荐组合**：单机令牌桶（快，挡住绝大部分）+ Redis 固定窗口做全局限额兜底（Lua 原子），并在文档里说明固定窗口的穿透问题及你为什么不选滑动窗口（内存 vs 精度的取舍）。

**限流维度**：用户 ID（防单用户刷）、SKU（防热点打崩）、IP（防脚本）；全局限流放在最外层兜底。

**被限流也要打指标**（`limiter_rejected_total{dimension="user"}`），否则你根本不知道限了多少、该不该调阈值。

### 7.8 对账：Redis 与 MySQL 的一致性

**差异的五个来源**（能列出来就说明你真跑起来过）：

1. Redis 预扣成功 → 进程崩溃/被 kill → DB 未落库
2. DB 落库失败 → 补偿 `HIncrBy` 也失败（Redis 抖动）
3. MQ 消息丢失或重试耗尽进 DLQ → Redis 已扣、DB 无单
4. 超时关单回补 Redis 成功、DB 更新失败（反向差异）
5. Redis 重启且未开 AOF（或开了但没刷盘）→ 预扣记录丢失

**对账算法：不能直接比 `available`**

这是最容易做错的地方。Redis 的 `available` 里含有**待支付订单占用的库存**（已预扣、还没支付），所以正确的口径是：

```
期望的 available = total_stock - sold_stock（已支付/已落库售出） - 待支付订单占用数量
差异 = redis_available - 期望的 available
差异 ≠ 0 才写入 reconcile_diffs
```

这就是 `reconcile_diffs` 表里必须有 `pending_orders` 字段的原因——**它是解释差异的中间态**，没有它，正常的待支付订单会被误判成差异。

```sql
-- 待支付订单占用量
SELECT COALESCE(SUM(quantity), 0) FROM orders WHERE sku_id = ? AND status = 0;
```

**修复策略（这里要做保守的工程取舍）**

| 差异情况 | 处理 |
|---|---|
| 差异 ≠ 0 且**活动已结束**（无并发写入） | 自动修复：以 DB 为准重算 Redis 并 `SET`，`status=1` |
| 差异 ≠ 0 且活动进行中 | 只记录 + 告警（`status=2` 需人工），**不自动改** |
| 连续两次检测结果一致 | 允许自动修复（确认不是瞬时中间态） |

**为什么不无脑自动修复**：修复过程中实时扣减还在发生，"读一个值 → 算期望值 → 写回去"三步之间库存可能已经被扣，写回会**覆盖掉真实扣减**，制造出新的超卖。所以要么停止写入，要么只做检测。**能主动说出这个风险，比写一个自动修复脚本更有价值**——这是本项目的核心面试素材之一。

**怎么验证对账有效**（写进测试）：

```sql
-- 构造差异 1：DB 扣了，Redis 没扣
UPDATE stocks SET available_stock = available_stock - 1 WHERE sku_id = 1001;
-- 构造差异 2：Redis 扣了，DB 没扣
--   redis-cli HINCRBY stock:1001 available -1
-- 构造差异 3：正常的待支付订单（不应该被报为差异 —— 防止对账误报）
```

跑对账任务 → 断言 `reconcile_diffs` 里恰好出现 1 和 2、不出现 3。**"断言不误报"比"断言能检出"更重要**，这是区分玩具实现和工程实现的分界线。

## 8. 可观测性

三件套：**日志**回答"这一次发生了什么"，**指标**回答"整体趋势如何"，**pprof**回答"时间花在哪了"。三者缺一不可，而且它们是互相引路的：指标发现 P99 抖了 → pprof 找到热点 → 日志确认业务影响。

### 8.1 结构化日志（`log/slog`）

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))
slog.SetDefault(logger)

logger.Info("order created",
    "request_id", rid, "order_no", orderNo,
    "user_id", uid, "sku_id", skuID, "cost_ms", cost,
)
```

**字段规范**（统一 snake_case，才能被日志系统按字段检索）：

| 字段 | 何时带 |
|---|---|
| `request_id` | 每个请求必有，由中间件从 `X-Request-ID` 取或生成 uuid，存入 context |
| `user_id` / `sku_id` / `order_no` | 业务上下文，异常日志必须有 |
| `cost_ms` | 请求出参与关键步骤耗时 |
| `err` | 错误日志的最后一位，值是 `err.Error()` |

**级别约定**：

| 级别 | 用途 | 例子 |
|---|---|---|
| Debug | 只在本地开 | 缓存命中详情、SQL 参数 |
| Info | 关键业务节点 | 下单成功、订单关闭、对账完成 |
| Warn | 可恢复的异常 | 补偿失败、MQ 重试、降级触发 |
| Error | 需要人介入 | 落库失败、对账发现差异、依赖不可用 |

**三条纪律**：

1. **不在循环里打日志**，压测时日志 IO 会直接变成瓶颈（先关 Debug 再压测，这是最基本的压测常识）。
2. **敏感信息脱敏**：密码、JWT、支付报文一律不入日志；**永远不要打印整个配置对象**——你的 RAG 项目里 `fmt.Printf("config：%+v")` 就是这么把 API Key 写进日志的。
3. 每个请求**最多**在入口和出口各打一条，业务层只在异常分支打。

## 12. 已知的坑

### 12.1 环境类

1. **Kafka `ADVERTISED_LISTENERS` 配错** → 客户端连不上或超时（见 3.2）
2. **Docker Desktop 资源限制让压测数据不可信**：WSL2 默认分走一半内存，且压测机与服务同机时 CPU 争抢。对策：压测前在 `.wslconfig` 里调好资源，压测报告里**必须写明环境**，别把数字说成"生产级"
3. **Windows 动态端口耗尽**：k6 高并发短连接会耗尽 TIME_WAIT 端口，表现为连接错误。对策：HTTP 长连接复用、`netsh int ipv4 set dynamicport tcp` 调大范围
4. **`localhost` vs `127.0.0.1`**：Node/k6 在某些环境把 `localhost` 解析成 IPv6 `::1`，而服务监听 IPv4 → 连不上，统一写 `127.0.0.1`

### 12.2 GORM 类（重点）

1. **软删除 + 唯一索引互相打架**：`DeletedAt` 非空的行仍占唯一键，删除后同 username 无法重新注册。复现：开软删除 → 注册 → 软删 → 用同名再注册 → 报唯一键冲突。**结论：本项目不用软删除**
2. **`Save` 会全字段覆盖**，并在并发下丢更新。扣库存一律用 `Updates` + `gorm.Expr` + 检查 `RowsAffected`
3. **默认复数表名**：`Order` → `orders`（`order` 是 SQL 保留字，正好避开）。字段名驼峰自动转下划线，别自己乱加 tag
4. **事务里的 ctx 与事务同生死**：`db.WithContext(ctx)` 用了带超时的 ctx，超时会连带取消事务。压测时超时设太短会看到大量"事务被取消"
5. **`PrepareStmt: true` 后改表结构要重启服务**，预编译缓存会失效
6. **时间精度**：`DATETIME` 不带 `(3)` 就没有毫秒，`expire_at < NOW()` 判定会有一秒级误差
7. **`ErrDuplicatedKey` 需要开 `TranslateError: true`**，否则只能自己解析驱动的错误码——而各驱动的错误码写法不一致

### 12.3 Redis 类

1. **`maxmemory-policy` 千万别用 `allkeys-lru`**：库存 key 被淘汰就等于超卖，用 `noeviction`
2. **热 key**：单个 SKU 的库存 key 天然是热 key。高级解法是**分段扣减**（把库存拆成 10 份 `stock:1001:0..9`，先随机选一段扣，扣不到再顺序找），代价是总量统计变复杂——这是个很好的"我考虑过但没做/做了之后数字变化"的素材
3. **Lua 脚本里不要遍历大集合**：Redis 单线程，脚本会阻塞所有请求
4. **大 key**：库存用 Hash 但字段只有两三个，别把订单列表塞进 Redis

### 12.4 并发类

1. **本地限流器用全局 `Mutex`** → 所有 SKU 抢一把锁，这正是 pprof 火焰图里最典型的发现，也是你的优化素材
2. **`map` 并发写**：本地缓存/限流器状态用 `sync.Map` 或分片锁；`-race` 能提前抓到
3. **goroutine 泄漏**：Kafka 消费者、定时任务忘了响应 `ctx.Done()`，压测多轮后 goroutine 数只增不减（用 pprof 确认）

### 12.5 Kafka 类

1. **开着自动提交但业务失败** → 消息静默丢失。必须手动提交，**处理成功才提交**
2. **一条坏消息卡死分区**（head-of-line blocking）→ 重试 3 次后进 DLQ 并提交 offset
3. **分区数只能增不能减**；**消费者数超过分区数就是浪费**
4. **rebalance 必然带来重复消费**，所以消费端幂等不是"可选优化"而是前提
5. 本地靠 `AUTO_CREATE_TOPICS_ENABLE` 省事，但要清楚生产环境是显式建 topic 并指定分区数
